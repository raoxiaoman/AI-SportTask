## 一、方案选型：Supabase

### 为什么选 Supabase

| 维度 | Supabase | Firebase | 自建 API |
|------|:--------:|:--------:|:--------:|
| KMP SDK 支持 | ✅ supabase-kt 官方维护 | ❌ 只有 Android SDK | ❌ 需自行开发 |
| 免费额度 | ✅ 足够个人使用 | ✅ 足够个人使用 | ✅ 仅需 VPS |
| 离线优先 | ✅ 可自定义 | 🔶 Firestore 原生支持 | ✅ 完全可控 |
| 学习成本 | 低（SQL 熟悉） | 中 | 高 |
| 数据所有权 | ✅ PostgreSQL 可导出 | ❌ Google 锁 | ✅ 完全自主 |
| 部署复杂度 | 低（托管） | 低（托管） | 高 |

**推荐：Supabase**

核心原因：
1. **supabase-kt** 是纯 Kotlin Multiplatform 库，Android 和 iOS 共用同一套代码
2. 使用 **PostgreSQL**，数据资产可迁移、可导出，不被锁定
3. 内置 **Auth**、**实时订阅**、**Row Level Security**，开箱即用
4. 免费版 500MB 数据库 + 5GB 带宽，对个人训练 App 绰绰有余

## 三、数据模型设计

### 3.1 本地数据库（现有 + 扩展）

现有的 SQLDelight schema 基本不需大改，只需增加同步相关字段：

```sql
-- 扩展: action_group 表增加同步字段
ALTER TABLE action_group ADD COLUMN sync_status TEXT DEFAULT 'local';  -- local/synced/pending
ALTER TABLE action_group ADD COLUMN updated_at TEXT;                    -- 最后修改时间 (ISO 8601)

-- 扩展: action 表增加同步字段
ALTER TABLE action ADD COLUMN sync_status TEXT DEFAULT 'local';
ALTER TABLE action ADD COLUMN updated_at TEXT;

-- 扩展: checkin 表增加同步字段
ALTER TABLE checkin ADD COLUMN sync_status TEXT DEFAULT 'local';
ALTER TABLE checkin ADD COLUMN updated_at TEXT;

-- 新增：同步元数据表
CREATE TABLE sync_metadata (
  key TEXT PRIMARY KEY,
  value TEXT
);
-- 存储 lastSyncTimestamp, userId 等信息

-- 新增：离线操作队列
CREATE TABLE pending_operations (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  operation_type TEXT NOT NULL,     -- 'INSERT', 'UPDATE', 'DELETE'
  table_name TEXT NOT NULL,         -- 'action_group', 'action', 'checkin'
  record_id INTEGER NOT NULL,
  payload TEXT,                      -- JSON 序列化的完整数据，用于冲突时重放
  created_at TEXT NOT NULL,
  retry_count INTEGER DEFAULT 0
);
```

### 3.2 云端数据库（PostgreSQL）

```sql
-- 用户表（Supabase Auth 自带 auth.users）
-- 应用数据表都通过 user_id 关联

CREATE TABLE cloud_action_group (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),  -- 用 UUID 避免冲突
  user_id UUID REFERENCES auth.users(id) NOT NULL,
  local_id INTEGER,                               -- 本地 ID（可选，用于映射）
  name TEXT NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW(),
  deleted_at TIMESTAMPTZ,                         -- 软删除
  UNIQUE(user_id, name)
);

CREATE TABLE cloud_action (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID REFERENCES auth.users(id) NOT NULL,
  local_id INTEGER,
  group_id UUID REFERENCES cloud_action_group(id),
  name TEXT NOT NULL,
  steps_text TEXT,
  default_time INTEGER NOT NULL DEFAULT 30,
  rest_time INTEGER NOT NULL DEFAULT 10,
  order_index INTEGER NOT NULL DEFAULT 1,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW(),
  deleted_at TIMESTAMPTZ
);

CREATE TABLE cloud_checkin (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID REFERENCES auth.users(id) NOT NULL,
  local_id INTEGER,
  date DATE NOT NULL,
  group_id UUID REFERENCES cloud_action_group(id),
  action_id UUID REFERENCES cloud_action(id),
  duration INTEGER,
  is_completed INTEGER DEFAULT 1,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW(),
  deleted_at TIMESTAMPTZ
);

-- 索引：按用户和时间查询
CREATE INDEX idx_action_group_user ON cloud_action_group(user_id, updated_at);
CREATE INDEX idx_action_user ON cloud_action(user_id, group_id, updated_at);
CREATE INDEX idx_checkin_user ON cloud_checkin(user_id, date, updated_at);
```

### 3.3 UUID vs 自增 ID 策略

| 方案 | 优点 | 缺点 |
|------|------|------|
| 本地自增 + 云端 UUID | 现有代码不需改，离线可用 | 本地云端 ID 映射复杂 |
| 全改 UUID | 无映射问题 | 需要改现有 SQLDelight schema |
| 混合（推荐） | 本地自增 ID 不变，云端用 UUID，sync_status 跟踪 | 映射层需维护 |

**推荐方案**：混合模式
- 本地继续用 SQLDelight 自增 ID
- 云端用 UUID
- `sync_status` 字段跟踪哪些记录需要同步
- 首次同步时建立 `local_id <-> cloud_uuid` 映射

## 四、同步策略

### 4.1 同步流程

```
[用户登录] → [首次全量上传] → [增量同步]
                │
                ▼
         本地数据全量上传
         建立 local_id → cloud_uuid 映射
         下载云端已有数据（如果有）
                │
                ▼
         进入增量同步循环
```

### 4.2 增量同步（Pull & Push）

```
                 云端
                 ▲  │
          Pull   │  │  Push
                 │  ▼
                 本地

PUSH:
  1. 查询 sync_status = 'pending' 的记录
  2. 按 updated_at 排序，分批上传（每批50条）
  3. 上传成功后标记 sync_status = 'synced'
  4. 更新云端 updated_at

PULL:
  1. 记录 lastSyncTimestamp
  2. 查询云端 updated_at > lastSyncTimestamp 的记录
  3. 下载差异数据
  4. 合并到本地数据库
  5. 更新 lastSyncTimestamp
```

### 4.3 冲突解决策略

| 场景 | 策略 |
|------|------|
| 本地修改 + 云端未改 | 直接上传本地版本 |
| 本地未改 + 云端修改 | 直接下载云端版本 |
| 本地修改 + 云端修改 | **Last-Write-Wins** — 比较 updated_at，新的覆盖旧的 |
| 本地删除 + 云端修改 | 删除优先（用户主动删 = 明确意图）|
| 本地修改 + 云端删除 | 上传修改（用户希望保留）|

### 4.4 离线支持

```
[用户操作] → [写入本地 SQLDelight] → [标记 sync_status = 'pending']
                                     → [写入 pending_operations 队列]

[网络恢复] → [SyncManager 检测到网络变化]
           → [按顺序执行 pending_operations]
           → [冲突时按策略解决]
           → [清空已完成的操作]
```

## 五、用户认证

### 5.1 登录方式

Supabase Auth 支持多种方式：

| 方式 | 复杂度 | 推荐度 |
|------|:------:|:------:|
| 邮箱 + 密码 | ⭐ 低 | ✅ 推荐（核心方式） |
| Google / Apple 第三方登录 | ⭐⭐⭐ 中 | 🔶 后续加 |
| 匿名登录（先体验再绑定） | ⭐⭐ 中低 | 🔶 不需要 |

**选择：邮箱 + 密码**（最简单，覆盖绝大多数用户场景）

### 5.2 认证流程

```
[用户] → [打开设置 → 登录页面]
       → [输入邮箱 + 密码]
       → [Supabase Auth 验证] → [获取 access_token + refresh_token]
       → [本地存储 token（Keychain/Keystore）]
       → [SyncManager 激活]
       → [首次全量同步]

离线时：本地 token 未过期可直接使用
        token 过期 → 用 refresh_token 刷新（后台静默）
        刷新失败 → 提示用户重新登录
```

### 5.3 多设备支持

```
[设备A] → [登录] → [同步数据到云端]
[设备B] → [同一账号登录] → [从云端拉取数据]
                           → [正常进入增量同步循环]
```

## 七、安全与隐私

### 7.1 Row Level Security (RLS)

```sql
-- 用户只能看到自己的数据
CREATE POLICY "Users can only see their own groups"
ON cloud_action_group FOR ALL
USING (auth.uid() = user_id)
WITH CHECK (auth.uid() = user_id);

-- 类似策略应用到 action、checkin 表
```

### 7.2 数据传输

- 全链路 HTTPS 加密
- Token 使用 Supabase 的 JWT
- 本地 token 存储在平台安全存储（Android Keystore / iOS Keychain）

### 7.3 数据删除

- 用户删除账户时，所有关联数据自动清除（CASCADE）
- 软删除（deleted_at）保留 30 天后彻底清除

## 📌 实际实现情况（2026-05-27）

> **注意**: 本项目最终选择了 **自托管后端（Node.js + Express + SQLite）** 而非 Supabase。

### 实际技术选型

| 维度 | 计划（Supabase） | 实际（自托管） | 原因 |
|------|:----------------:|:--------------:|:----:|
| 后端 | Supabase 托管 | 自建 Node.js VPS | 已有 Racknerd VPS，零额外成本 |
| 数据库 | PostgreSQL | SQLite | 单用户场景，SQLite 足够且免运维 |
| 认证 | Supabase Auth | JWT (bcrypt + jsonwebtoken) | 轻量，自建完全可控 |
| HTTP 客户端 | supabase-kt | Ktor Client | Ktor 是 KMP 官方推荐，更通用 |
| 项目结构 | cloud 包 | data/remote 包 + cloud 包（并行） | 双实现可灵活切换 |

